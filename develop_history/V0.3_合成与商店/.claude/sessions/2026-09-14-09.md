# 2026-09-14 会话 09 —— 挂机状态：躺着 / 结算界面 / 读图界面都不许闪回「游戏中」

接会话 48（`2026-09-14-04.md`）那套挂机判定。用户实机跑了一遍，报三处：

> 「挂机过程中，如果死了，等待复活的几秒会变成游戏中，复活后恢复成挂机中，
> 我希望等待复活过程中不要重置为游戏中，而是维持死前的状态」
> 「然后结算界面和开局加载界面，好像也会变成游戏中？这个也要维持上一次的状态」

**三处同一个根因**，结论在 **D125**，这儿只记流水账。

## 改了什么

`conn_is_afk()` 里那条「躺着一律不判」原来是 `return False`（= 显示游戏中）：

```python
-    if dead_since is not None: return False
+    if dead_since is not None: return afk_when_down      # 倒下那一刻定格的结论
```

`Conn.afk_when_down` 新增；`note_seat_died()` **先定格再上闩**；
`note_seat_respawned()` / 新一局一起解冻；`note_seat_settled()` 那条绕路
（第五轮为躲「躺着」豁免而用 `conn_afk_clock_expired()`）收回成 `conn_is_afk()`。

## ★ 为什么这一处能连累到结算界面和读图界面

挂机的人**每局把三条命全用光**（实测 2.8~3.0 次/局，§111），最后那次死透之后
`dead_since` 就一直挂着 —— 结算界面 15 秒、回房间、下一局读图 7.5 秒，
全程都走那条 `return False`。⇒ **一晚上真正显示「挂机中」的只有零星几秒。**

## ★★ 这一轮真正的收获：那条**端到端**用例

`test_battle.AfkAcrossTheWholeRoundTests` —— 进图 → 挂机 → 被打死 →
结算界面 → 回房间 → 按 F5 读图 → 再进图 → 按一下方向键，逐段断言。

**那三处我本来全都有单独的用例，而且全是绿的。** 漏掉的是「串成一条链」：
房间状态在结算界面和读图界面仍然是「游戏中」，而判据在中间某一段被重置了。
★ 拿修复前的代码跑这条链**当场红**（`'afk_quest' != 'play_quest'`）。

⇒ 以后再动挂机判定，**先看这条链**。
