# 2026-09-15 会话 57 —— 成就防刷：bot 受限的那一局不计成就

用户原话：「V0.3.3 我加了成就卡片掉落系统。发出去后，发现有人建一个房间，
加入 bot 然后用 hold 命令把 bot 定住后打 bot 刷成就。我想改一下，加个限制 ——
bot 必须能自由活动没有限制的情况下，击杀 bot 才会计算成就，任何能限制 bot
活动的命令（/hold，/w 非零参数，以及其他调试参数）执行后，都停止计算成就。
bot 难度必须大于等于 2 才计算成就。有的命令会跨局生效，跨局时，这个成就获得
限制也要生效。加入已有的房间，且这个房间应用了 bot 限制命令，则成就获得限制
也要生效。」

口径全部写进 **D127**，这里只记流水。

## 开工前问的四个口径（用户当场拍的）

1. 触发之后什么时候恢复 → **限制解除后下一局恢复**（不是永久拉黑房间）
2. 「不计成就」的范围 → **战绩不进账 + 不发卡**（经验 / 金币 / 材料照发）
3. 脏房间里没有 bot 的那些局 → **「局内出现过 bot 限制，则当局不算；下一局
   bot 全踢掉也恢复正常」**，外加一条追加要求：**每局 log 都要写清楚计算或
   不计算的原因**
4. 提示 → **触发时发一行 + 每局开头再提醒一行**

## 做了什么

**只动服务端三个文件**（`bot.py` / `gameserver.py` / `run_tests.py`）+ 新测试模块。
`lobby.py` 最后一个字都没改 —— 原方案里那个 `Room.bot_limit_told` 标志位被
「按命令前后的实况比」取代掉了（见下面的返工 ③）。

* `bot.py`：`BOT_FREEDOM_FIELDS`（五个开关的单源表）、
  `BOT_DIFFICULTY_MIN_FOR_CARDS = 2`、`LIMITING_COMMANDS` / `HARMLESS_COMMANDS`
  （归类检查表，不是运行时判据）、`bot_limit_reason(room)`、`note_bot_limit()`、
  `handle_command()` 收尾的前后两扫 + 首次提示、钩子 `gameserver.BOT_LIMIT_REASON`
* `gameserver.py`：钩子槽 `BOT_LIMIT_REASON` + `bot_limit_reason_now()`、
  模块级 `room_system_chat(room, text)`、唯一工厂 `new_room_quest()`（两个建点都改走它）、
  `RoomQuest.bot_limit_reason` 一格、结算处的判定 + 两条日志 + 跳过累计/发卡、

* `server/test_cardfair.py`（新，43 条）+ 登记进 `run_tests.MODULES`

## 三处返工（都是**审查时读代码**读出来的，不是跑出来的）

写完方案之后先让一个 Plan agent 对着代码逐条审，结果三条都成立：

1. ★★ **`broadcast_start_game` 的 `self` 可能已经不在房里** ——
   `after_someone_left()` 是在 `LOBBY.leave(self)` **之后**调的
   （`gameserver.py` 的 `leave_room`），它那条「等的人走了，放行」会一路走到
   收尾块。原方案用 `Conn.room_system_chat()`，而 `Conn.broadcast()` 第一句就是
   `room = self.lobby_room(); if room is None: return 0` ⇒ 那一局的提示只会发给
   **刚走掉的那个人**，房里一个都收不到、还不报错。
   ⇒ 改成模块级 `room_system_chat(room, text)`，从 `room` 出发发包。
2. ★★ **`RoomQuest` 有两个建点**：正常开局 + `quest_state()` 的懒惰兜底
   （控制通道 / 协议试探走那条）。原方案只接了前一个。
   ⇒ 做成唯一工厂 `new_room_quest()`。
3. ★★ **结算路径上不许 lazy `import bot`**：`bot.py` 被 import 的那一刻就把四个
   钩子装进 `gameserver`，而 `test_battle` **不 import bot** ⇒ 跑到第一个结算用例时
   会中途把 bot 驱动装上，之后所有用例的行为跟着变（并行分片下还是「跑到哪个
   用例才变」的时序依赖）。⇒ 走现成的钩子模式。

★ 另外把 `Room.bot_limit_told` 那个标志位删了：**踢掉受限的 bot 不走命令层**，
标志位会永久卡在 True。改成「比这一次命令前后的实况」，顺带省掉一个字段。

## 自己给自己挖的两个坑（都是跑出来 / 量出来才发现的）

* ★★ **宽度用例只量了 `/hold`**。六种原因里 `/noboom`（57 宽）和 `/slow`（59 宽）
  都超了 50 —— 而 `/hold` 是 44，只量它一条都拦不住。人话改短（去掉括号里的解释），
  用例改成**六种逐个量**，并且拿「把解释加回去」验过它真的会红。
* ★★ **用例里重复调 `self.setUp()`**。`BattleRoom.setUp` 会把**当前**的
  `gameserver.PEER_RELAY` 存成待还原值，再跑一次就把还原链套娃了 ⇒ 这一片跑完
  `PEER_RELAY` 停在一个夹具对象上，同一个进程里后面的
  `test_udpsync.DeliverRoutingTests` 当场红。症状很像「偶发」：第一次全量红在
  3.14、第二次红在 Win7，单跑那个模块又永远绿。
  ⇒ 改成「用增量比两局」和「把 bot 手动恢复自由」，不再重入 setUp。
  **教训写进了那个 helper 的 docstring。**
* 收尾把前后两扫抽成 `_scan_bot_limit()` 时顺手让**命令之前**那一扫也会播报 ——
  于是敲一条 `/d 3` 都会刷一行。`test_a_second_limiting_command_does_not_repeat_it`
  当场红。⇒ 加了 `announce=False`。（记这一笔是因为它说明那条去重用例真的在干活。）

## 第二轮（同一天，用户实机跑完 4 局之后）

用户报：「最后一局我开局前先定住 bot、再解除，随后调难度 1，然后又调难度 2，
这时应该解除限制才对，但进入游戏还是提示难度为 1，没有成就，这个要修。」
另外要求「解除限制后，成就恢复时也打一个消息提示」。

### 查下来：服务端没算错，是敲错了命令

`logs/server.out` 那一段（`/d` 的日志是**无条件**打的，全程只有 `-> 1`，没有 `-> 2`）：

```text
23:31:48  /hold: [(1, True)]                    定住
23:31:54  聊天 '/hols'                          ← 打错，当普通聊天广播掉了
23:31:58  /hold: [(1, False)]                   解除
23:32:12  /d: bot 难度 -> 1                     难度 1
23:32:20  聊天 '/b 2'                           ← 想敲的是 /d 2，又打错
23:32:28  /r: 座位 [1] 的 bot 已准备
23:32:36  开局 → 成就判定: 本局不计成就 —— 开局时 bot 难度只有 1
```

⇒ 难度从头到尾是 1，判定**是对的**。不认识的 `/xxx` 被当普通聊天原样广播是
**故意的**（`handle_command` 第一道闸 `return False`），不然正常聊天里以 `/`
开头的话都会被吞。

### 真正的毛病是**没有回执**，于是改了

敲完屏幕上什么都不动 ⇒ 分不清「解除成功」和「命令压根没生效」。
所以用户第二轮要的那句话不是锦上添花，**它就是这条判据的可观测性**（D127 ⑥）：

* `_scan_bot_limit()` 的状态翻转**两个方向都说**：受限 → 一行；
  解除 → `⚠ bot 限制已解除，下一局起重新计成就。`
  原因只是**换了一种**（放开 `/hold` 但难度还是 1）时两边都非空 ⇒ 一句不说。
* 文案说**下一局**：局中解除时这一局的闩不撤，说「恢复了」会把人骗一次。
* 新用例组 `UserReportedSequenceTests` 把他那一串按键**逐键复现**，
  **敲对 / 敲错两个方向都钉住**：`/d 2` ⇒ 恢复计成就且有回执；
  `/b 2` ⇒ 仍然不计且**一个字都不说**（这正是辨别办法）。

两套运行时 **3663 项全绿**（净增 9）。新增的两道拦网也逐条打断验过
（拿掉「解除」那一支 ⇒ 5 条红；让它在「原因换了一种」时也乱说 ⇒ 1 条红）。

⚠ 顺带记一笔：`launch.ps1` 的调试日志开关叫 **`-DebugLog`**，不是 `-Verbose`
（`-Verbose` 是 PowerShell 的公共参数，传了不报错但没效果）。

## 第三轮（同一天，用户看过第二轮的文案之后）

用户点了两条：

1. **游戏中**解除限制时，那句话后面再加个括号写明「本局不生效」；
   **在房间里**解除时不要这个括号。
2. **结算界面**上，如果因为 bot 限制没算成就，也发一条提示；正常结算不发。

### 落地

* 「解除」那一句拆成**基句 + 结尾**：`BOT_LIMIT_CLEARED_NOTICE` +
  `BOT_LIMIT_CLEARED_IN_ROUND`（`（本局不生效）。`）/ `BOT_LIMIT_CLEARED_IN_ROOM`（`。`）。
  判据是 **`RoomQuest.bot_limit_reason` 上没上闩**，不是「房间状态是不是游戏中」
  —— 回房间时 `room.quest` 被置 None，所以房间里那一支天然不带括号。
  ⚠ 带括号那句 **48 宽**（上限 50），所以基句里「重新计成就」缩成了「计成就」；
  用例**两种结尾都量**。
* 结算提示 `⚠ 本局开启过 bot 限制，不结算成就。`（35 宽）排在结算三连发
  **之后** —— 结算界面是第一发 `0x0411` 弹出来的，先发就落在界面后面了。
  走房间级 `room_system_chat(room, …)`，一局一句（不进逐座位循环）。

**3669 项全绿**（净增 6）。五道新拦网逐条打断验过：括号一律加 / 一律不加、
结算提示删掉 / 不管脏净都发 / 排到结算包之前，每种都当场红。

⚠ **这一版改完没重启服务端** —— 用户当时开着客户端（前两轮我连着把它关了两次）。
写这行是提醒下一个会话：**验之前先 `stop.bat` → `start.bat`**。

## 顺带发现，没动，等用户拍板

★ **`0x040f → 0x0405 → 0x040f` 可以无限重复结算，一个 bot 都不用。**
`reset_room_for_next_round()` 把 `room.quest` 置 None，那道
`if quest.settled: return` 的门跟着没了；下一发 `0x040f` 会新建一个
`settled=False` 的 `RoomQuest`，**替房里每一个人**重新入账经验 / 金币 / 材料 /
对局数 / 卡片。和「用 bot 刷」不是一回事，而且改法涉及「这一局结算过了」这件事
该记在哪（`room.battle`？代号？），单独决策。写在 D127 ⑩。
